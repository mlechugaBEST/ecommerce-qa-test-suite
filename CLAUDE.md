# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A multi-store Cypress end-to-end test suite that verifies customer-facing forms and pages on the Best Access Doors family of live BigCommerce storefronts. One shared set of specs runs against any store; each store is described by a JSON file in `stores/`. No application code lives here — only test code.

Stores: BESTUS (bestaccessdoors.com — the default), BESTCA, ADAP, ADC, AAP, FSE, BRH, CAD, PDA (all nine fully configured).

## Commands

**Browser default is Chrome.** The `npm` scripts and both runner scripts force `--browser chrome` (see "Browser Baselines"); pass an explicit `--browser firefox` to override. Bare `npx cypress run` still defaults to Electron — prefer the `npm`/launcher paths.

**Non-technical launchers (Windows, double-click — see `READ ME FIRST.txt`):** `First Time Setup.bat` (bootstraps Node, then `npm install` + `cypress install`/`verify`), `Run All Tests.bat` (→ `npm run test:all`), `Run One Store.bat` (menu → `npm run test:store <code>`). All Chrome, all keep their window open with results.

**Node bootstrap (`scripts\ensure-node.bat`):** all four launchers `call` this first; it guarantees a usable Node on `PATH` and is the single source of truth for the pinned version (`NODE_PIN`, currently **24.19.0**). Rungs, first hit wins: repo-local portable Node in `tools\` → an already-installed system Node that passes the version gate → a Node MSI/ZIP dropped in `installers\` → a machine-wide winget/MSI install (**opt-in only**, needs UAC: set `SETUP_MACHINE_NODE=1`) → download the official ZIP and unpack into `tools\` (**the default**, needs no admin) → fall back to printing manual nodejs.org instructions. Downloads are SHA256-verified against nodejs.org's `SHASUMS256.txt` before anything is executed or extracted. Both `tools\` and `installers\` are gitignored, so bundling an installer for an offline/locked-down machine is a per-deployment choice needing no code change.

Things about that file that are load-bearing and easy to break:

- **It must never contain `setlocal`.** Callers reach it via `call`, so the `PATH` it sets survives into the launcher; a `setlocal` would discard it and portable Node would vanish on return. It also deliberately avoids delayed expansion — every `for /f` capture is read after its loop ends.
- **`curl`/`tar`/`certutil`/`findstr` are invoked by absolute `%SystemRoot%\System32\` path.** Git for Windows ships GNU tar as `tar.exe`, which cannot read `.zip` at all and shadows Windows' bsdtar whenever its `usr\bin` precedes System32 on `PATH`.
- Inside `for /f ('...')` those tool paths are **unquoted** — a leading quote makes cmd mis-parse the whole command line. File arguments stay quoted.
- winget/msiexec results are checked with `if not "%ERRORLEVEL%"=="0"`, never `if errorlevel 1`: winget returns HRESULTs like `0x8A15010C` that cmd sees as *negative*, so `errorlevel 1` misses every failure. Their exit codes are logged but never branched on — the ladder re-probes for `node.exe` instead, which collapses declined-UAC / winget-absent / already-installed into one behaviour.
- `%ProgramFiles(x86)%` is hoisted to a top-level variable, because expanding it inside an `if (...)` block closes the block early on its literal `)`.
- x64 is forced even on ARM64 Windows: Cypress publishes no Windows arm64 binary, so native arm64 Node would break its download.
- The launchers use `pushd "%~dp0"`, not `cd /d`, so a UNC path (`\\server\share\…`) works instead of silently running in `C:\Windows\System32`.
- **`:__en_probe_portable` matches the exact pin first, then falls back to any `tools\node-v*-win-x64` that still passes the gate.** Pass 2 is what stops a `NODE_PIN` bump from stranding existing deployments: without it the old folder stops matching and the three *detect-only* launchers demand a re-run of First Time Setup even though a usable Node is sitting right there. Verified live — with the pin at 24.19.0 and only `node-v22.23.2-win-x64` on disk, detect-only still succeeds on 22.23.2.
- **Watch for `The system cannot find the batch label specified` in the output.** cmd's label lookup here proved sensitive to *where* labels land in the file: a first draft of `:__en_probe_portable` used two helper labels calling each other, and cmd printed that error intermittently — appearing and disappearing as unrelated lines were added nearby, while the ladder still worked. It is now one helper (`:__en_pp_cand`) reached only from `for` bodies. If you add or move a label in this file, re-check for that line.

**Node version gate (and why Node 26 is rejected):** `package.json` `engines.node` mirrors Cypress's own range (`^20.1.0 || ^22.0.0 || >=24.0.0`), but `ensure-node.bat`'s `:__en_gate` accepts only majors **22 and 24** — deliberately stricter at *both* ends. Node 20 is rejected because it went EOL **April 30 2026**; an unknown-new major is rejected because Cypress 15.15.0 unzips its binary via `extract-zip` 2.0.1 → `yauzl` 2.10.0 (a 2017 package declaring only `engines: ">= 10.17.0"`), and on **Node 26.7.0 `cypress install` prints "Unzipping Cypress" and then stops — exiting 0 while leaving no `Cypress.exe` behind**, so only the explicit `cypress verify` step catches it (exit 1). Verified against isolated `CYPRESS_CACHE_FOLDER`s: **24.19.0 good** (download + unzip + verify + `homepage.cy.js` 13/13, Aug 14 2026), **22.23.2 good** (Aug 12 2026), **26.7.0 unusable** (Aug 12 2026, re-confirmed Aug 14 2026). Rejecting costs only a portable Node install beside the tests; wrongly accepting hands the operator a broken Cypress. **The unblock condition for Node 26 is already known: Cypress ≥ 15.16.0 replaced that stack with `yauzl ^3.3.1`** — so bump Cypress first, re-verify, then add the major to `:__en_gate` **and** `scripts/nodeGate.js`. Full reasoning, the dated verified-combo log, and the copy-pasteable verification procedure live in **`MAINTENANCE.md`**.

**`scripts/nodeGate.js` (warn-only Node check):** the launchers can't be bypassed by accident, but `npm run test:all` straight from a terminal skips `ensure-node.bat` entirely and inherits whatever Node is on `PATH`. `run-all.js` and `run-store.js` each call `warnIfUnsupportedNode()` at require time: it prints a block to **stderr** naming the running version and pointing at the launchers, and **never changes the exit code** — `cypress run` itself is fine on Node 26, only `cypress install` breaks, so blocking a run that would have passed would be worse than the problem. Its `ACCEPTED_MAJORS` is a deliberate mirror of `:__en_gate`; change both together. Not wired into `scripts/dashboard/server.js` — it spawns those runners with inherited stdio, so the warning already reaches the dashboard log pane. **A `DEP0205 module.register()` warning in run output is the tell that a run is on Node ≥ 26** (the warning does not exist on 24 or 22), i.e. that the bootstrap was bypassed; it comes from inside the Cypress binary bundle, not from anything in this repo.

**`npm install` alone does not finish setup:** npm 11.x gates install scripts, so Cypress's `postinstall` never runs and no browser binary is fetched. `First Time Setup.bat` therefore runs `node node_modules\cypress\bin\cypress install` and `… verify` explicitly (invoking the bin JS directly rather than via `npx`, to avoid shim resolution). Without that step setup reports "ALL SET!" and then every run fails.

```bash
# Install dependencies (once)
npm install

# Run all tests headlessly against the default store, BESTUS in Chrome (stub mode — no real leads created)
npm test                   # = cypress run --browser chrome

# Run a single spec file
npm test -- --spec "cypress/e2e/contact-form.cy.js"

# Run against a specific store (run-store.js injects --browser chrome unless you pass --browser)
npm run test:store bestca
npm run test:store -- aap --spec "cypress/e2e/homepage.cy.js"   # extra args forwarded to cypress run

# Run every store sequentially (continues on failure, summary table at the end; run-all.js injects --browser chrome)
npm run test:all
npm run test:all -- --stores bestus,bestca

# Open interactive Cypress app in Chrome (default store; restart after editing a stores/*.json)
npm run test:open
npx cross-env STORE=bestca cypress open --browser chrome

# Live submission mode (creates real Zoho CRM leads — use sparingly)
npm run test:live

# Friendly browser dashboard (non-technical front end; double-click "Test Dashboard.bat")
npm run dashboard          # serves http://localhost:8420 (override port: DASHBOARD_PORT)
```

**Test Dashboard** (`scripts/dashboard/`, launcher `Test Dashboard.bat`): a local browser UI for non-technical operators — pick stores, watch a live run, see color-coded per-store cards with inline failure screenshots/videos, run history, and one-click re-run of failed specs. It is purely additive and does **not** change how Cypress runs: the Node `http` server (built-ins only, zero new deps) *spawns* `scripts/run-all.js` / `scripts/run-store.js`, so the `after:run` hook keeps writing `results/.run-summary/<store>.json` (which the UI reads for card state) and `results/test-results.log` (which the History tab parses). Stub-only by design — the server strips `LIVE_SUBMIT`/`I_KNOW_THIS_IS_LIVE` from the child env, so the dashboard can never create real leads; live mode stays CLI-only. Store display names live in `scripts/dashboard/storeNames.js`. Front end is `scripts/dashboard/public/` (`index.html`/`app.js`/`styles.css`) — brand palette (blue `#498cbc`, yellow `#ffd200`, black/white) driven by CSS variables with a **light (default) / dark** theme toggle persisted to `localStorage("dashboard-theme")` and applied pre-paint by an inline `<head>` script; status-tier colors (green/red/orange) are intentionally non-brand for health legibility.
**Dashboard security**: `server.js` binds `127.0.0.1` only (never reachable from another device on the LAN) and validates every `--spec`/store value from `POST /api/run` against real on-disk files/store codes before they ever reach a `spawn()` call — no shell is invoked, so no injection surface. On top of that, the 3 state-changing routes (`/api/run`, `/api/stop`, `/api/exit`) require an `X-Dashboard-Token` header matching a random token generated at server startup and injected into `index.html` via a `<meta name="dashboard-token">` tag (read by `app.js`, attached to its `fetch` calls) — closes the CSRF/other-local-process gap that loopback-binding alone doesn't. Read-only GET routes (`/api/stores`, `/api/results/latest`, `/api/history`, `/api/stream`) stay unauthenticated by design. The token rotates on every restart, so a stale already-open tab needs a reload after the dashboard restarts.

## Multi-Store Architecture

- `cypress.config.js` reads `process.env.STORE` (default `bestus`), loads `stores/<STORE>.json`, sets `baseUrl` from it, and injects the whole object into `Cypress.env('site')` plus `STORE`. Screenshots/videos go to per-store subfolders (`cypress/videos/<store>/`). The loader throws with the list of available codes on an unknown store and sanity-checks `storeCode`/`baseUrl`/`homePath`. It also runs a non-throwing shape check: any top-level key or `forms.*` key not in its known-keys allowlist prints a `console.warn` (never throws) — catches a typo'd key (e.g. `frms` instead of `forms`) that would otherwise silently render as an identical-looking `[skipped: not configured for CODE]` in every gated spec. Extend the allowlists when a new top-level or `forms.*` section is introduced.
- `cypress/support/store.js` is the only module that reads `Cypress.env('site')`. It exports:
  - `getStore()` — the store config object, available synchronously at spec module-evaluation time (this is why config is injected via env rather than `cy.fixture()` — `describe` vs `describe.skip` must be decided at collection time)
  - `describeIfStore(condition, title, [options,] fn)` / `itIfStore(condition, title, fn, [reason])` — run the suite/test when the config section exists, otherwise `describe.skip`/`it.skip` with a `[skipped: not configured for <CODE>]` title suffix so missing features show as pending, never silently absent. `itIfStore`'s optional `reason` replaces that suffix with `[skipped: <reason>]` for _deliberate_ gates (theme lacks the element, form doesn't require the field, Electron-only limitation) so the skip self-documents to anyone running the suite — e.g. `[skipped: store theme hides breadcrumbs on mobile (pdp.mobileBreadcrumbsHidden)]`. Omit `reason` only for genuine "not configured yet" gates on scaffold stores.
  - `storePath(path)` — appends the store's `visitQuery` if set (AAP needs `?redirect=disable` on every visit)
  - `homePath()` — the store's homepage path (FSE's homepage is `/new-home/`, not `/`)
- **Nullable-section contract** in `stores/*.json`: `plp`, `products`, `discovery`, `pdp`, and each entry under `forms` may be `null`, which makes the specs gated on them skip. `storeCode`, `baseUrl`, `homePath`, `branding.copyrightText`, and `branding.imageHosts` are required. `branding.footerLocationText`, `branding.warehousesLink`, and `branding.partnerLinks` may be `null` (their individual homepage tests skip). See `stores/bestus.json` for the full shape; a scaffold (not-yet-onboarded) store carries a `_todo` key describing what to fill. **All nine current stores are fully onboarded** — no scaffolds remain; the `_todo`/`describeIfStore` machinery stays for the next store added.
- **Absent-feature registry (`_absentFeatures`)**: every store config carries an `_absentFeatures` array documenting each feature verified absent on the live site (Pro Club, Become Vendor, architects form, subcategory taxonomy, no-results search state, …). Each entry names the `configKey` to fill when the feature launches, the `fillWith` shape, the `verifiedAbsent` evidence/date, and the spec(s) it `enables`. Filling the key auto-enables the skipped specs — no code change needed. When a store launches a new form/feature, sweep its `_absentFeatures` first; when onboarding discovers a new absence, add an entry instead of leaving the null undocumented.
- Store-specific text lives in config, not specs: brand/copyright text, footer location, PLP heading/breadcrumb labels (`plp.mainHeading`/`plp.breadcrumbLabel` — Spanish on PDA), search terms, sort label.
- **Footer theme drift**: stores run different BigCommerce footer themes, so footer selectors/expectations are config-driven. `FOOTER_DEFAULTS` in `store.js` holds the BESTUS values (`footer.tcsFooter`, `.box h3`, `.Contact-info-box`, `.Copyright p`, 2+ tel links); any key can be overridden per store via `branding.footer` (see `stores/bestca.json`, which uses `footer.footer`, `h5.footer-info-heading`, `.contactbox`, `.footer-copyright p`, 1 tel link). `footerConfig()` returns the merged result; `assertFooterHeadings` and both homepage specs read from it.
- **Header theme drift**: some themes have no semantic `<header>` element (ADAP's desktop header is `div.desktop-header-section`, its mobile header `div.iPad_header`). `headerSelector()` / `mobileHeaderSelector()` in `store.js` default to `header` and are overridden per store via `branding.headerSelector` / `branding.mobileHeaderSelector` (mobile falls back to desktop). Consumed by both homepage specs, `pdp.mobile.cy.js`, and `assertMaxTouchTarget`. Likewise the mobile nav drawer: `MOBILE_NAV` in `devices.js` resolves via `mobileNavSelector()` (default `div.mobile-menu`; ADAP and AAP both override to `#mySidenav` via `branding.mobileNavSelector`).
- **PLP/PDP theme drift**: same pattern — `PLP_SELECTOR_DEFAULTS` / `PDP_SELECTOR_DEFAULTS` in `store.js` hold BESTUS selectors (PLP `heading`, breadcrumbs, sidebar, subcategory boxes + their `subcategoryTitle`/`subcategoryLink` internals, `productCard` grid container, `cardPrice`, per-card `cardImage`/`cardTitle`/`cardLink` internals, gallery image, description, related carousel, product-info-form container, qty stepper buttons, `pdfNewTab`), overridable per store via `plp.selectors` / `pdp.selectors` (see `stores/adap.json`, `stores/bestca.json`, `stores/adc.json`). Nullable selector keys (`breadcrumbHome`, `sidebar`, `bestSellers`, `subcategoryBox`, `cardPrice`, `relatedCarousel`, `productInfoForm`, `qtyIncrement`, `qtyDecrement`) skip their check when set to null — use for stores whose theme lacks the element (ADC sets `cardPrice: null` because its mixed catalog interleaves priced and quote-only cards). `assertBreadcrumbs`/`assertProductInfoForm` read from `pdpSelectors()`; `productCardSelector()` (exported from `checks.js`) reads `plp.selectors.productCard`; `assertProductCards` reads `plp.selectors.cardImage`/`cardTitle`/`cardLink`/`cardPrice` (`cardLink` is one combined-selector string, e.g. `.card-figure a, .card-title a` — whichever anchor matches on the theme, `.first()` picks it) and `plp.cy.js`/`plp.mobile.cy.js` read `plp.selectors.heading`. No fleet store overrides `cardImage`/`cardTitle`/`cardLink` yet — they exist purely as the escape hatch for the next theme whose card-inner markup diverges (previously these 3 were hardcoded directly in `checks.js` with no override contract at all).
- **BESTUS known deficiencies (bestaccessdoors.com — the baseline store)**: no theme drift to document — its selectors ARE the `PLP_SELECTOR_DEFAULTS`/`PDP_SELECTOR_DEFAULTS`/`FOOTER_DEFAULTS` baseline every other store overrides from. Two live-verified defects are **skipped** (not left failing — a deliberate exception to the site-deficiency policy below, same sanctioned-skip precedent as AAP/FSE's touch-target gap), both documented in `stores/bestus.json` `_notes` (July 23 2026): (1) the Pro Club form (`/pro-club-application/`) correctly blocks submission when Email is empty (`cy.expectNoSubmission()` passes) but the `Email_error` message never toggles visible (confirmed live via direct DOM inspection — still `display:none` 1.5s+ after submit) — a Zoho form-config gap isolated to this one field; `forms.proClub.emailErrorNotVisible: true` gates only the `cy.expectFieldError()` call in `pro-club-form.cy.js`, the functional no-submission check still runs unconditionally. (2) `/content/assets/js/tracking_code.js` — loaded only on `/request-a-quote/` (confirmed via a script-tag diff against `/contact-us/`, which doesn't load it) — is deployed with literal `<script type="text/javascript">`/`</script>` wrapper tags still inside the file content: a Zoho UTM/lead-tracking snippet meant for inline embedding, mistakenly saved as a standalone external file. Loaded via `<script src>`, the browser parses the raw text as JS and throws `SyntaxError: Unexpected token '<'` with no stack at all (same redacted shape as a cross-origin error, despite being same-origin) on every quote-form page load. Real-world impact is low: the actual Zoho form/submission is independent code and unaffected (manually verified) — only this script's own UTM-attribution cookie logic silently never runs on that page. Suppressed via a `messagePattern` entry in `checks.js`'s `KNOWN_BUGGY_SCRIPTS` list (see the Global Setup section below), since the error carries no stack to match on a host/path. Fix means re-uploading `tracking_code.js` without the wrapper tags, or embedding the snippet inline instead of via external `src`.

## Browser Baselines

All specs (except `lighthouse.cy.js`) are browser-agnostic and pass in both Chrome and Firefox. `lighthouse.cy.js` skips itself automatically when run in anything but Chrome (so it now runs on every default invocation).

**Chrome is the default for all entry points** — `npm test`, `npm run test:open`, `npm run test:live` hard-code `--browser chrome`, and `run-store.js`/`run-all.js` push `--browser chrome` onto the cypress args unless the caller already passed `--browser`. This means Lighthouse runs by default and several previously Electron-only skips (e.g. BESTCA's `skipMobileTouchTarget`) no longer apply on a normal run.

```bash
# Chrome baseline (the default everywhere — also runs Lighthouse)
npm test                              # or any npm/launcher path
npx cypress run --browser chrome      # explicit equivalent

# Firefox baseline (override; lighthouse.cy.js is skipped automatically)
npm test -- --browser firefox
npx cypress run --browser firefox
```

## Architecture

### Stub vs. Live Mode

By default, all Zoho form POST requests are intercepted and replaced with a fake success response. No real data reaches the CRM. Live mode requires **both** `LIVE_SUBMIT=true` and `I_KNOW_THIS_IS_LIVE=true` environment variables set simultaneously — this double-gate is intentional.

The `cy.interceptZoho(alias, urlPattern)` custom command handles this via `setupZohoIntercept()` in `cypress/support/utils/zohoIntercept.js`.

**Stub-mode catch-all (the safety net in `e2e.js`):** `cy.interceptZoho()` stubs only the ONE `submitUrlPattern` a store has configured, so if a live form is *renamed* that pattern silently stops matching and the POST is not intercepted at all — it reaches Zoho for real and creates a genuine CRM lead during what is supposed to be a stub-mode run. This is not hypothetical: BESTUS PDPs were re-pointed from `BESTProductForm` to `BESTCAProductForm` in Aug 2026 (a storefront-side embed mistake, since corrected) and `product-form.cy.js` filed two real leads per run until it was caught — the tell was `cy.wait('@submit')` reporting "No request ever occurred" *about the route*, while the browser had in fact POSTed normally. So a global `beforeEach` in `e2e.js` also registers a catch-all `POST **/forms.zohopublic.com/**/submit` stub whenever `isLiveSubmit()` is false. Because it is registered before the per-spec `cy.interceptZoho()` (which runs inside the test body) and **Cypress matches routes in reverse order of definition**, the later, narrower named intercept still wins on a healthy store and aliases behave exactly as before — verified empirically with a throwaway spec, not assumed. On drift the catch-all absorbs the POST instead: no lead is created, while `cy.wait('@submit')` still times out and the test still fails, so the red signal is unchanged. Absorbed URLs are reported from an `afterEach` via `cy.task('log', …)` as `[zoho-catchall] absorbed …`, which is the direct tell that a store's `submitUrlPattern` has gone stale. **Known gap:** `cy.expectNoSubmission()` also watches the named alias, so it still passes *vacuously* when a pattern is stale — the catch-all neither helps nor hurts there, and the happy-path failure in the same spec is what surfaces the drift. The live-mode double gate is shared: `isLiveSubmit()` is exported from `zohoIntercept.js` and used by both `commands.js` and `e2e.js` so the two can never disagree on what counts as live.

### Page Object Hierarchy

All form page objects extend `ZohoFormPage` (the base class in `cypress/support/pages/ZohoFormPage.js`), which provides common Zoho field selectors (`input[name="Name_First"]`, `input[name="Email"]`, etc.) and a `submit()` / `expectSuccess()` method.

Subclasses add form-specific fields:

- `ContactFormPage` — adds address fields, inquiry type dropdown, message textarea, and file attachment
- `QuoteFormPage` — adds model (`SingleLine1`), size (`SingleLine2`), quantity dropdown, address (`SingleLine3`)
- `ProClubFormPage` — adds address fields and country dropdown
- `ProductFormPage` — takes `site`, `productUrlOverride`, and `randomize` constructor args; uses `pickProduct()` to resolve the product URL; adds `fillDetails()` for the `MultiLine` textarea

### Custom Commands (`cypress/support/commands.js`)

- `cy.uniqueEmail()` — generates a timestamped test email from the store config's `testEmailTemplate`
- `cy.fillPersona(formPage, persona, email)` — duck-typed: calls fill methods on the page object only if they exist, so the same persona object works across all forms
- `cy.interceptZoho(alias, urlPattern)` — sets up stub or passthrough intercept based on env flags
- `cy.expectNoSubmission(alias = 'submit')` — asserts a form did NOT submit. Waits briefly before checking `@<alias>.all` has length 0, because an instant check trivially passes before a delayed/async POST could land — used by every form spec's "does not submit" and per-field validation tests
- `cy.expectFieldError(selector)` — asserts a Zoho validation error is visible for the field matched by `selector`. Scopes to the field's own `.zf-tempFrmWrapper` (Zoho's own per-field container) and asserts `be.visible`, not `exist` — Zoho pre-renders every field's error `<p class="zf-errorMessage" style="display:none;">` into the DOM unconditionally, so existence alone is never a meaningful signal that validation actually fired

### Fixtures and Store Configs

- `stores/<code>.json` (NOT a Cypress fixture — loaded by Node in `cypress.config.js`) — canonical per-store source for base URL, `homePath`/`visitQuery` quirks, branding text, PLP paths/labels, form paths, Zoho submit URL glob patterns, product URLs (`products.known`), PDP URLs (`pdp.popular`), discovery inputs (`discovery`: search terms/`expectedTokens`, representative `categories`, `mobileCategory`, `multiPageCategory`, and `sort` label/param/value), and `testEmailTemplate`
- **PDP pick attribution**: `pdp.cy.js`, `pdp.mobile.cy.js`, `seo.cy.js`, `images.cy.js`, and `lighthouse.cy.js` each call `pickRandom(site.pdp.popular)` to choose one product per run — a failure otherwise gives no signal about which product was hit. Each call site logs the picked URL via `cy.task('log', …)` (reaches the real process stdout — visible in a terminal run, `run-store.js`/`run-all.js`'s inherited stdio, and the dashboard's live log pane, unlike `cy.log()` which only reaches the in-browser Command Log and is invisible in headless `cypress run`) paired with a `cy.log()` for interactive `cypress open` reproduction. This is attribution only — there is no exclude/pin mechanism, since one would risk masking a genuine site deficiency (e.g. CAD's documented PDF gap below) in violation of the site-deficiency policy.
- **Call-for-pricing SKUs inside otherwise-priced catalogs**: large/freight-class equipment (roof hatches, smoke vents, quad doors) can be "call for pricing" — no price, no qty input, no Add to Cart, no lead-time widget, just a product-info-request form — even on stores whose catalog is otherwise fully priced (confirmed live on ADC, e.g. `/48-x-72-quad-safemax-steel-smoke-vent-babcock-davis/`). This is real, intentional business behavior for big-ticket items, not a site deficiency, and it isn't confined to one store the way `pdp.quoteOnly` (BRH's whole-catalog flag) is — so it can't be expressed as static per-store config, and curating/excluding specific `pdp.popular` URLs would mean auditing the whole fleet's lists and staying fragile to future catalog changes. Instead, `pdp.cy.js`, `pdp.mobile.cy.js`, and `seo.cy.js` detect it **at runtime, per picked product**: after `cy.visit`, they check whether `sel.addToCart` (`#form-action-addToCart`, never null) exists on the page; if it's absent, the price/qty/Add-to-Cart/lead-time assertions (`pdp.cy.js`/`pdp.mobile.cy.js`) and the JSON-LD `offers.price`/`priceCurrency`/`availability` assertions (`seo.cy.js`'s `assertProductJsonLd({ requirePrice: false })`) are skipped for that one run via `this.skip()` inside the `it()` body rather than `pdp.quoteOnly`'s collection-time `itIfStore` — combined with a `cy.task('log', …)` line so the skip is still visible in terminal/dashboard output even though Mocha's dynamic skip doesn't carry `itIfStore`'s title-suffix reason. `pdp.quoteOnly` still short-circuits the same checks for BRH (a true whole-store fact, cheap to check at collection time) — the two mechanisms are additive, not a replacement of each other.
- `personas.json` — fake customer data used as form input; `primary` is the only persona currently defined and is shared by all stores. A store can localize any persona field via a top-level `personaOverrides` object in its `stores/<code>.json`, merged over the fixture by `storePersona()` in `store.js` (used by all six form specs). The fixture persona is Canadian (Waterloo, ON), so every store whose market is not Canada carries an override: **AAP, ADAP, BESTUS, BRH, CAD and FSE** use a US address with `country: "United States"`, **PDA** a Mexico City address with `country: "Mexico"`, and **ADC / BESTCA** need none. The `country` value must match the market *and* the address, because it is now selected explicitly on the contact form (see `ContactFormPage.selectCountry`) rather than left on whatever the theme preselected — before Aug 2026 five US storefronts were quietly submitting a Waterloo, ON address labelled "United States". The string must match an `<option>` exactly: all nine country lists are **English-labelled**, so PDA is `"Mexico"`, not `"México"` (a mismatch makes `cy.select()` fail loudly rather than silently no-op)

### Global Setup (`cypress/support/e2e.js`)

Runs before every test: imports `cypress-real-events`, and calls `blockThirdParty()` (from `checks.js`), which stubs every host in its `THIRD_PARTY_HOSTS` list with an empty 204 by default — GA, GTM, GA Connector, Zoho PageSense, Meta, Reddit, Spotify, Taboola, leadsy, iovation, Geotargetly, Affiliatly, SearchSpring's tracking beacons, Zoho SalesIQ's backend endpoint, Clarity, ipapi.co, door-pay.com (BRH's tax-exempt form widget, whose `bc_tax_exempt_form_load.js` throws `setting 'hostUrl'` on every BRH page load — a vendor-script bug, blocked so it never runs). A couple of entries serve a small real script body instead of an empty one, when the live site's own first-party bootstrap code assumes the blocked script already ran: e.g. BESTUS's inline bootstrap calls `gaconnector2.track(id)` 3s after page load assuming GA Connector already defined that global, so its stub defines a no-op instead. The host list was derived by auditing every resource the live site loads; store-functional vendors (SearchSpring search API, Yotpo reviews, Zoho forms, PayPal, fonts, library CDNs, Klaviyo) are deliberately left loaded. See the `blockThirdParty()` doc comment in `checks.js` for the rationale.

The `uncaught:exception` handler is narrowly scoped, not a blanket suppressor — it swallows an exception only when it's attributable to something other than first-party product code: (1) a browser-redacted cross-origin script error (Same-Origin Policy strips all detail; matched on Cypress's own fixed wording, not the bare browser message, since Cypress wraps the redaction rather than passing it through) — this arm matches **two** shapes of the same SOP redaction: a thrown error (`/cross origin script/i`) and an unhandled *rejection* whose non-Error reject value Cypress's `makeErrFromObj` wraps as `An unknown error has occurred: [object Object]` (`/an unknown error has occurred/i`). The rejection shape was added July 29 2026 for FSE, where SearchSpring's cross-origin Snap bundle (`snapui.searchspring.io`, store-functional) throws `t.isImmediatePropagationStopped is not a function` on a PLP product-card click (diagnosed live via chrome-devtools; site still works because the card `href` navigates; not FSE-fixable — SearchSpring's code; see `stores/fse.json` `_notes`). It surfaced once the handler was narrowed (commit `aedddf9`) from the old blanket `() => false`; a genuine first-party regression throws an `Error` with a real message+stack and never produces the opaque wrapper, so this stays safe; (2) an error whose stack traces to a `THIRD_PARTY_HOSTS` entry, or (3) an error matching a `checks.js` `KNOWN_BUGGY_SCRIPTS` entry — either by stack (a vendor script deliberately left running for real that has a known internal bug of its own, e.g. Zoho SalesIQ's widget UI bundle) or by message (a same-origin script that still loses its stack because it's loaded as a raw external `<script src>`, e.g. BESTUS's malformed `tracking_code.js` — see the BESTUS bullet above; and a `/(fbq|analytics|gtag|ttq) is not defined/` message entry for pixel/analytics globals that ADAP/ADC call from their own inline page code but that go undefined because `blockThirdParty()` stubs the vendor library (Meta Pixel, Segment-via-GTM) — a first-party-stack ReferenceError with no blocked host to match on, so suppressed by message like `tracking_code.js`; the same error fires in prod for adblock users and loses only a tracking call; an ADAP `/.fancybox is not a function/` message entry for its theme calling a jQuery lightbox plugin before it loads; and a `messagePattern: /Failed to fetch/` entry for the Klaviyo email-capture popup, which is left loaded because the popup is store-functional (AAP/PDA/BRH) but whose telemetry `logMetric` fire-and-forgets a fetch that fails under Cypress — an unhandled `Failed to fetch` rejection that is third-party noise, not a store defect. It's matched by message rather than stack because the frames it does carry are `klaviyo.js` and BigCommerce's `csrf-protection-header` fetch wrapper — neither is a `THIRD_PARTY_HOSTS` entry (Klaviyo is deliberately left loaded), so no `stackPattern` would fire; this is safe because `uncaught:exception` fires only for *unhandled* rejections and every fetch our specs actually assert on is awaited/caught. That entry now only comes into play on visits that don't install the `makeConsoleErrorSpy` fetch wrapper — see the spec-frame paragraph below). This batch of first-party theme errors (fbq/analytics, fancybox) surfaced only because the `uncaught:exception` handler was narrowed from a blanket `return false` to this scoped form (commit `d05ca7a`, the exception-scoping security fix) — the old blanket handler swallowed them all; the scoped handler correctly surfaces first-party regressions but also these benign theme-noise throws, so each is added back by message. The fancybox case is a genuine first-party theme bug documented in the store `_notes` with the dev team notified — suppression keeps the rest of the suite runnable, a temporary measure, not a substitute for the fix. Any other exception — including a real, attributable first-party stack — fails the test as normal, the same as any other assertion failure.

**The `uncaught:exception` handler only sees APP-frame errors (spec-frame errors are unsuppressable):** Cypress binds `error`/`unhandledrejection` listeners on both the AUT window (`frameType: 'app'`) and the spec window (`frameType: 'spec'`), and `cy.onUncaughtException` emits the `uncaught:exception` event **only** when `frameType === 'app'` (verified in the Cypress 15 runner bundle). A spec-frame error therefore fails the test unconditionally — no `THIRD_PARTY_HOSTS` or `KNOWN_BUGGY_SCRIPTS` pattern can rescue it. Tell the two apart by the error text: a spec-frame failure reads "originated from your **test code**" and omits Cypress's usual "you can choose to turn this off by listening to the `uncaught:exception` event" sentence, which only the app-frame template carries. This bit us once (fixed Aug 2026): `makeConsoleErrorSpy`'s fetch wrapper in `checks.js` used to `return Promise.reject(err)` from its `.catch`, and since the wrapper is spec-bundle code running inside the AUT, the promise it returned was attributed to the spec frame — turning Klaviyo's fire-and-forget `logMetric` "Failed to fetch" rejection into an unsuppressable spec-frame failure that killed `pdp.mobile.cy.js`'s `before all` hook (skipping a whole device suite, un-retryable) despite the matching `KNOWN_BUGGY_SCRIPTS` entry. The wrapper now logs `[fetch failed] <url>` on a **side branch** (`p.catch(log); return p;`) and hands back the original promise, so it handles the rejection at the source and never creates a rejected promise of its own; app code that awaits a failed fetch without catching still rejects in the app frame and stays triageable. **Rule for support-file code that runs inside the AUT** (this fetch wrapper, the BRH `setTimeout` wrap below): handle async failures at the source, and never return a promise you leave rejected — the `uncaught:exception` handler cannot reach it.

**BRH document-ready throws (the `setTimeout` wrap in `e2e.js`):** BRH's theme has multiple bugs in its jQuery `document.ready` callbacks — it calls `.trim()` on an undefined value (`Cannot read properties of undefined (reading 'trim')`) and calls `$(...)` when `$` is not a function (`$ is not a function`) — first-party theme bugs that throw on BRH pages (and for real users). jQuery runs `.ready()`/`Deferred` callbacks asynchronously via `window.setTimeout`, so a throw inside one propagates out of that timer as an uncaught error that — confirmed live over several runs — does **not** reach the `uncaught:exception` handler above in any suppressible way (not by message, not by stack, nor via a capture-phase `error` listener; the old blanket `() => false` hid them, which is why BRH looked green before `d05ca7a`). So they're prevented at the source: a `Cypress.on('window:before:load')` in `e2e.js` wraps the BRH window's `setTimeout` and swallows any throw whose stack shows the jQuery+`bestroofhatches.com` ready channel (a `code.jquery.com` frame **and** a `bestroofhatches.com` theme-callback frame). Scoping by that stack signature — not by message — covers trim, `$ is not a function`, and any further ready-callback bug in this theme in one shot, without masking an unrelated error (which wouldn't carry that jQuery+host stack), and lets the PDP/discovery/images suites run their real assertions instead of dying in `before all`. A `[BRH-DIAG] setTimeout-swallowed …` counter is logged per spec via `cy.task('log')` (a temporary diagnostic). Documented in `stores/brh.json` `_notes`; BRH devs must fix the theme's document-ready scripts, then remove the wrap.


### Anti-automation Countermeasures (`cypress.config.js`)

Chrome launches with a spoofed user-agent and `--disable-blink-features=AutomationControlled` to avoid bot-detection on the live site. Timeouts are set conservatively (15s default command, 60s page load, 30s response) to account for real network latency. Default viewport is 1920×1080.

### Payload Inspection Pattern

When verifying that form values are actually sent, tests use `getMultipartField(body, fieldName)` from `cypress/support/utils/getMultipartField.js` to parse the multipart/form-data request body from the intercepted Zoho POST.

### Mobile Testing Pattern

Mobile specs use `cy.viewport(width, height)` per device in `beforeEach`. The `footer.tcsFooter` element and `.categories-left` sidebar are `display:none` on mobile — tests assert DOM presence rather than visibility for these. Touch target tests measure `getBoundingClientRect()` heights of visible interactive header elements against thresholds (44px for phones, 24px for tablets) — see `assertMaxTouchTarget` in `checks.js`. Two skip flags exist: `branding.skipMobileTouchTarget` skips the touch-target test **in Electron only** (a rendering limitation — it still runs in Chrome/Firefox; only BESTCA sets it), while `branding.skipTouchTarget` skips it **in every browser** (a known header touch-target deficiency the store's dev team has reviewed and chosen to keep as-is — AAP and FSE set it; the sanctioned exception to the leave-it-failing site-deficiency policy). Both gates live in `homepage.mobile.cy.js` and `pdp.mobile.cy.js` with self-documenting `itIfStore` skip reasons. The **no-horizontal-overflow** check (`assertNoHorizontalOverflow`) runs inside a retryable `cy.get('body').should(...)` closure so Cypress re-measures until layout settles — this absorbs a flash-of-unstyled-content race (an image with no `width`/`height` attribute briefly rendering at its natural width before the theme stylesheet clamps it; PDA's 418px-intrinsic header logo triggered a phantom ~466px overflow on the old single-shot measurement). Genuine overflow never settles, so it still fails. Per-store `branding.overflowIgnore` still excludes named third-party widgets.

### Adding a New Form Test (see `architect-form.cy.js` / `ArchitectFormPage.js` for a recent example)

1. Create a page object in `cypress/support/pages/` extending `ZohoFormPage`; read its `path` from `getStore().forms.<name>.path` (`ArchitectFormPage.js` is the minimal case — just a few extra field methods; `BecomeVendorFormPage.js` overrides `submit()` for a custom-built form)
2. Fill the form's `{ path, submitUrlPattern }` in each store's `stores/<code>.json` that has the form (the `forms.architectInquiries` slot already exists as `null`); leave it `null` for stores without it
3. Create a spec in `cypress/e2e/` following the existing pattern: module-level `const site = getStore()`, outer `describeIfStore(site.forms && site.forms.<name>, ...)` gate, `before()` loads the personas fixture, `beforeEach()` instantiates the page, `describe('Happy path')` covers success + payload, `describe('Validation')` covers empty/malformed fields

### Adding a New Page/Layout Test

1. Create a spec in `cypress/e2e/` — no page object needed for read-only page checks
2. Read store data via `getStore()` from `cypress/support/store.js` at module level; gate the suite with `describeIfStore` on the config section it needs, and use `storePath()`/`homePath()` for visits so per-store quirks apply
3. For a matching mobile spec, reuse the same device matrix defined in the existing mobile specs
4. Block analytics and suppress third-party exceptions via the global `e2e.js` setup (already applied automatically)

### Onboarding a Scaffolded Store

1. Open the store's `stores/<code>.json` — the `_todo` key lists what's missing
2. Verify `branding.copyrightText` (and optionally `footerLocationText`, `warehousesLink`, `partnerLinks`) against the live footer
3. Fill `plp`, `products`, `forms`, `discovery`, and `pdp` using `stores/bestus.json` as the reference shape — each section you fill automatically enables its specs on the next run
4. For non-English stores (PDA), all user-visible text values in the config must be the localized strings from the live site
